### How the requirements reached the tools
We loaded the project brief and SRS PDFs directly, then used them as the spec for the whole build: page list, table schema (Customers / Reservations), reservation logic (30 tables, random assignment, conflict handling), and menu content all came straight from the SRS rather than being invented.

- Generated the Flask backend (app.py, models.py, config.py) — routes, SQLAlchemy models, and input validation — in one pass, then iterated based on actual test failures.
- Generated the full React front end: routing shell, five pages, shared Navbar / Footer / Lightbox components, and the CSS design system (tokens, Grid/Flexbox layout, responsive breakpoints).
- Used AI-assisted design judgment for the visual identity (typography pairing, colour palette, the "printed menu" motif on the Menu page) rather than defaulting to a generic template look.
- Images for the website were generated by AI with specific design and theme instructions in the prompts.
- Text for the website was generated with AI tools, with human review for clarity and style.

### What the AI generated vs. what we changed by hand

- **Generated largely as-is:** the initial project structure, some React components and page layouts, the basic Flask setup, SQLAlchemy models, and some of the starting CSS.
- **Generated then substantially reworked by hand:** the reservation and table availability logic, newsletter and database integration, responsive navigation, form validation, styling and content, error handling, and setup documentation. We also adjusted AI-generated code whenever testing uncovered issues or it didn't fit what we needed.
- **Written by hand:** the final design and content decisions, image selection and placement, application and database testing, configuration troubleshooting, and the fixes made while integrating the parts.

### How we worked together
Work was divided by lane — Jay on content, visual direction and QA; San on full-stack integration; Lan on the database and requirements — and tracked against weekly deadlines through to submission.

### What worked well

- Generating the backend and frontend together in one coherent pass kept the API contract (field names, response shapes) consistent on both sides without extra glue code.
- Having the AI run the Flask app against its test client caught two real bugs before we ever touched the browser: a missing db.session.flush() before reading the new customer's ID, and a duplicate-email edge case on the newsletter endpoint.
- Vite build confirmed the whole React app compiles cleanly (no broken imports or JSX) before we treated it as done.

### What didn't work / limitations
The AI tools had no PostgreSQL instance or browser of their own, so the backend was first validated against SQLite as a stand-in and the front end by production build rather than a live click-through. Both were subsequently smoke-tested locally against real PostgreSQL and through the running site.

Testing was verification-oriented rather than a maintained test suite, consistent with the brief's note that significant testing is out of scope for this project.

### 2.3 Lan Yun — QA for Database and AI Documentation

**Tools I used personally:** Claude Cowork (Opus 5), Gemini

**What I used them for:**

- PostgreSQL installation and local database setup
- SRS traceability matrix — extracting all 40 requirements from the SRS into a numbered, checkable set
- A set of requirement-labelled API checks, built from that matrix, that exercise any running backend over HTTP
- Database QA against the delivered backend: schema inspection, constraint verification, and concurrency testing
- Demo database seeding and the before/after queries used in the recorded demo
- A pull request fixing reservation validation for past-dated time slots (SRS FR-7)

**A specific example:**

**What I asked for:** I asked Claude to turn the SRS traceability matrix into something executable — a set of checks where each one is labelled with the requirement ID it verifies, so results could be read straight back into the matrix.

**What it produced:** A black-box set of 16 checks that talks to a running backend over HTTP rather than importing its code, so it works against any implementation of the API contract. It covers the fields the reservation form must accept, past and malformed dates, malformed email address, the 30-table limit, the fully-booked rejection, newsletter validation, and response times.

**What I changed:** Running them against the delivered backend surfaced a concurrency defect. Forty simultaneous booking requests returned forty confirmations across only twenty-eight distinct tables — the same table was confirmed to multiple reservations, and the restaurant was overbooked without the "fully booked" message appearing. The cause was that the availability check and the insert were not atomic. It was fixed with a unique constraint on (time slot, table number) plus a retry so a losing request quietly receives a different table. The same checks also found that the API accepted bookings dated in the past, which I fixed myself and submitted as a pull request.

**Overall:**

**What worked well:** It helped with my database configuration. It explained unfamiliar terminal and database errors, my API appearing to return nothing at all, which turned out to be macOS AirPlay Receiver occupying port 5000 and answering with an empty 403.

**What didn't work:** Two things. The traceability matrix became too detailed to use as a day-to-day tracker, so it served as coverage guidance rather than a progress tool, and I chose not to add that documentation burden to the team. More importantly, my first set of checks used fixed time slots computed from the current date, so on a second run it targeted slots the first run had already filled. Every booking came back "fully booked," and the check for "the 31st booking is refused" passed — for entirely the wrong reason, because the slot was already full before the test began. A test that passes for the wrong reason is more dangerous than one that fails.

**How I verified its output:**

- Installed and configured PostgreSQL 16 locally, applied the DDL, and inspected the result with \dt and \d reservations to confirm the tables, primary keys, foreign key, unique constraint, and indexes matched the SRS.
- Exercised every endpoint by hand and confirmed each status code: 200 health, 201 confirmed booking with a table number in range, 400 malformed timestamp, 409 fully booked, 400 invalid email, 201 newsletter signup, and 400 for a past date.
- Confirmed the concurrency fix at three independent levels rather than trusting a passing test: (1) declared — the unique constraint present in models.py; (2) enforced — \d reservations showing the constraint in the live table, which matters because db.create_all() never alters tables that already exist, so code can be correct while the running database is not; (3) observed — 30 confirmations across 30 distinct tables, no duplicates.
- Cross-checked the demo script against the live schema before recording, which caught two queries — both used id where the columns are customer_id and reservation_id.
